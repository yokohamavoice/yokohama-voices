# ヨコハマの声：試作版の集計方法
## データと参加単位
一つの匿名回答セッションを1行、投稿を1列とします。賛成=-1、反対=+1、パス=0、未回答=nullです。同じ人の再参加は別セッションです。初期意見は市の資料を参考に作成した40件で、回答は一切捏造していません。
「無関係」は独立した回答として保存し、分析では未回答と同じ扱いで除外します。データベースでは value=0 と unrelated=1 の組で記録し、通常のパス（value=0、unrelated=0）と区別します。画面用APIでは値2として返し、PCA・クラスタリング・共通点の賛成率の計算には含めません。
掲載承認済みで、自分の投稿でも回答済みでもない意見から、サーバーで抽選します。方式は tag-mixture-v2 で、Polis標準のroutingとは異なります。詳細は後述します。
## Polisに由来する処理
Copyright (C) 2012-present, The Authors. AGPLv3。
参照コード: https://github.com/compdemocracy/polis/tree/28b427324f751c8f1e42ab5df3d5111fe9f26db0/math/src/polismath/math
pca.clj と conversation.clj の一部をTypeScriptへ移植しています。
未回答を列の観測平均で補完し、中心化した行列にpower iteration（最大100回、収束時は早期終了）とdeflationで2軸のPCAを適用します。座標は観測回答だけの内積に sqrt(投稿数/回答数) を掛けます。パスは観測された0で、未回答と区別します。
グループ横断の賛成度は、各群について (賛成数+1)/(回答数+2) を計算し、それらの積とします。回答数にはパスを含み、未回答は含みません。これは投稿内容の論証の正しさを評価するものではありません。
## 試作版独自の条件・簡略化
6件以上の賛成・反対を回答した80セッション以上が必要です。3回答以上ある投稿が6件以上あること、少なくとも3件の共通した賛成・反対回答で全対象セッションがつながることを確認します。
PCA座標に直接k-means（2〜4群、各群3セッション以上）を行い、silhouetteが最も高い分類を選びます。0.45未満の場合は分類を保留します。これは人工回答での検証に基づく暫定値で、離散的な集団の存在を証明する基準ではありません。Polis本体のbase-cluster圧縮や更新間smoothingは使わないため、完全互換ではありません。
全群で10件以上の回答、かつ60%以上の賛成がある投稿のうち、各群の賛成率のWilson下限（連続性補正なし、z=1.96）が0.5を超えるものを共通点候補とします。パスは分母に含み、未回答・無関係は除きます。10回答なら9賛成、20回答なら15賛成が必要です。この下限は固定された独立二項標本での両側95%区間の下端に相当しますが、このサイトでは表示のための目安として使います。同じ回答による群・意見の選択、適応的な配信、繰り返しの計算を補正した検定ではなく、誤発見率や真の賛成率60%以上を保証しません。表示は合意の証明ではありません。意見群のラベルには政治的意味を付けません。座標や分類は回答が増えると変わります。
分析対象の1,000セッション上限はありません。対象全員をPCA、k-means、共通点集計に含めます。入力は票を分割して読み込み、欠損を含む回答表を1セル1バイトで保持します。PCAは投稿間の共分散を用い、参加者どうしの総当たりを避けます。グループ数の選択に使うシルエット係数だけ、各群最大256対象・128比較点の決定的な標本で近似し、群の人数で重み付けします。小さい群は全点を使います。結果に近似の有無と方式を記録します。

設定値は `lib/polis-math.ts` の `DEFAULT_ANALYSIS_OPTIONS` に集約しています。Wilson下限は `(p + z²/(2n) − z√(p(1−p)/n + z²/(4n²))) / (1 + z²/n)`（p=賛成数/n）で計算します。参考: https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm 。人工回答で候補値を比較し、実回答で再評価する暫定運用です。

分析結果はアルゴリズムの版と全設定値を付けた共有の固定スナップショットとしてR2に保存します。全体の再計算は毎日午前3時（日本時間、UTC 18時）の定期処理で行い、回答や結果閲覧では起動しません。同時アクセスは完成済みの同じ結果を使い、更新処理中も直前の有効な結果を返します。新しい結果は保存を完了してから切り替えます。掲載判断・本文・計算の版・設定値が現在と一致しない結果は配信せず、次の全体更新を待ちます。過去のスナップショットは上書きしません。

回答時は、保存したPCAの対象投稿・列平均・2本の軸を用い、今回のセッションだけをブラウザで投影します。対象投稿に対する賛成・反対が6件以上ある場合に暫定位置を表示します。観測された回答だけの中心化内積に sqrt(対象投稿数/観測回答数) を掛け、パスは観測回答、「無関係」と未回答は欠損として扱います。日次更新後の新しい投稿は次回更新まで投影に含めません。色は保存済みグループ中心への最近傍で決めます。日次の群人数や共通点は変更せず、暫定位置を二重の輪で重ねます。日次の各群の全点から凸包を求め、表示上の余白を加えた薄い領域と件数を描きます。個々の点は切り替えで表示します。領域は点の広がりの可視化であり、所属判定には保存済み中心への距離を使います。描画範囲は日次の地図から決めて固定し、範囲外の暫定位置は端に表示します。

日次処理では全対象データを読み直し、前回のPCA軸を初期値に使います。前回の群所属を新しいPCA座標へ対応させて中心を計算し直し、k-meansの初期値に使います。独立した初期値からの候補も比較し、前回の解を固定しません。前回の状態を引き継げない場合は通常の初期値から開始します。前回の回答表をそのまま答えとして使うものではなく、新しい回答を含めた全体の解を更新します。

ブラウザは初回に地図と投影用の値を取得し、ページが見えている間は60秒ごとに新しいスナップショットの有無だけ確認します。同じIDなら地図全体は再送しません。集計閲覧履歴にはスナップショットIDを記録します。セッションIDの内部対応表と次の日次計算に使う群所属はブラウザへ送りません。

意見ごとの4種類の回答数、回答済みセッション数、回答総数は投票と同じDB処理内で差分更新します。重複回答は加算せず、非表示・復元では承認済み集計への出入りだけ反映します。意見の抽選は保存済み件数と当該セッションの履歴を読み、過去の全票を再集計しません。

## 提示方法（tag-mixture-v2）
候補のある分野数をT、そのセッションですでに配信した分野tのカード数をh_tとします。分野の確率は q_t = 0.20/T + 0.80 × (1+h_t)^(-2) / Σ_t (1+h_t)^(-2) です。画面への表示確認とは別に、サーバーで配信した枚数を使います。

分野内の意見iについて、a=賛成数、d=反対数、n=a+d、N=パス・無関係も含む全回答数、s=(a+1)/(n+2) と置きます。賛否の割れ方の重み D_i=4s(1-s)n/(n+8)、回答の少なさの重み U_i=(1+N)^(-1/2) とします。

分野t内の候補数をm_tとして r_i=0.30/m_t+0.40 D_i/ΣD+0.30 U_i/ΣU、最終確率は q_t r_i です。ΣD=0のときはその成分を分野内均等にします。混合成分を選んだ場合の確率ではなく、混合後の最終確率を保存します。すべての候補に正の確率があり、共通賛成が高い投稿も表示対象に残ります。比率は運用上の初期設定で、効率の最適性を検証したものではありません。

未回答の配信を1件ずつ保持し、再読み込み・再送で引き直しません。掲載判断が変わって配信を取り消した場合は取消時刻を残して次を選びます。回答済み、自分の投稿、未承認、非表示の投稿は選びません。

## 原記録
impressionsには提示ID、セッション内順序、本文・タグ（名称と説明を含む）・出典のスナップショット、配信方式、選択確率、全候補とその件数・確率、配信時刻、表示通知受信時刻、回答時刻、取消時刻を保存します。

eventsには表示通知、集計結果の閲覧、閲覧タブ、画面の可視状態・離脱通知、明示的な回答終了・セッション終了を保存します。集計閲覧はその時点の集計スナップショットに結びつきます。ブラウザイベントは受信時刻に加えて端末の時刻とそのページ内の順番を保存します。端末時計は正確とは限らず、順番は再読み込みで再開します。終了操作などサーバー側イベントには端末時刻がない場合があります。

ブラウザの通知は読んだ証明ではありません。終了通知や通信に失敗する場合があり、最後の記録は正確な退出時刻を保証しません。配信だけされて表示確認がないもの、表示後の未回答、パス、無関係を区別します。案内の版は保存しますが、これを研究への明示的同意の取得記録とは呼びません。研究上必要な手続きは具体的な研究計画に合わせて行います。

## 掲載判断
新規投稿はpendingとして保存します。管理者の承認後にapprovedとなり、参加画面・一覧・集計に入ります。hidden/rejectedはそれらから除外します。管理者だけが理由を付けて承認・却下・非表示・復元・継続掲載できます。本文は上書きしません。

前回確認した時点から無関係が3件増えた投稿、または新しい通報がある投稿を管理者の確認一覧に出します。件数だけでは掲載状態を変えません。確認コードに含まれる件数だけを確認済みにするため、判断待ちの間に増えた通報は残ります。判断は版番号と操作IDを使って重複や古い状態への適用を防ぎ、理由・担当者・実行元を履歴に残します。

## 解説と公開データ
読みやすい解説は /technology、研究利用と保存範囲の案内は /research を参照してください。原データは非公開のデータベースに保持し、管理者認証付きAPIだけで取得できます。精密な時刻や行動履歴を公開GitHubへ自動送信しません。

公開候補を時点固定して保存し、管理者が候補のJSONとSHA-256を確認してから公開します。/api/export は最新の承認済みの版、?list=1 は公開版一覧、?release=公開版ID はその固定版を返します。未承認の候補は公開APIから取得できません。候補に含む投稿の判断が変わったら、その候補の公開を止めます。

公開データschema_version=3には掲載承認済みの本文・分野・出典と、セッション単位の回答、提示順・抽選確率・表示通知/回答/取消の有無を含めます。投稿者と回答者の対応、認証情報、回答・表示の詳しい時刻、通報者、結果閲覧や画面離脱の詳細記録は含めません。自由記述や回答の組合せによる個人の推測を完全に防げるわけではありません。

プロジェクト専用のGitHubには承認済みの各版だけを原則毎時保存します。公開版のJSONは変更せず、releases/公開版ID/ に保存します。保存済みデータは、後で投稿を非表示にしても自動削除されません。

公開候補は500原行ずつ、本文・回答・提示のJSONLページへ分割し、途中から再開できます。20,000投稿・100,000回答・100,000提示の一括上限はありません。開始時に確定済みレコード番号の上限と掲載判断の版を固定します。あとから届いた回答が古い時刻を持っていても混入しません。ページ一覧も分割し、各ファイルのSHA-256をルートのJSONからたどって確認できます。GitHubには分割したまま保存し、旧schema 2も引き続き読み込めます。

これは無制限の容量・処理時間を保証するものではありません。利用するホスティングのDB容量・クエリ数・CPU・メモリ制限は別にあります。特に投稿数と一人あたりの回答数が大きくなると分析負荷は増えます。提示候補履歴は従来どおり全候補と確率を保存し、1記録1,500,000文字の保護上限を設けています。
